1 Propósito y alcance
Este documento define cómo el frontend y los integradores autorizados consumen el backend de Excelencia Inmobiliaria. Traduce las decisiones arquitectónicas y los agregados del dominio a rutas, solicitudes, respuestas, permisos, errores y garantías observables. La API propuesta usa REST con JSON para operaciones ordinarias, WebSocket para chat humano y un adaptador de webhooks para pagos. El chatbot inmobiliario conserva su interfaz HTTP independiente.
El documento y su contrato complementario openapi.json constituyen una propuesta revisable, no evidencia de implementación o aprobación. Se conserva un monolito FastAPI con nueve módulos, MySQL privado, almacenamiento externo privado y tareas programadas separadas. No se incluyen citas, visitas, negociación, contratos legales, cierre de operaciones, reparto de comisiones ni notificaciones automáticas de matching.
Las rutas, DTO, límites de payload y códigos específicos definidos aquí son precisiones nuevas de diseño. Las reglas abiertas de los documentos anteriores siguen pendientes. Ninguna ruta habilita cobros reales, sanciones o publicaciones con políticas sin resolver. Los usuarios y administradores no escriben tablas ni activan periodos pagados mediante un cambio directo de estado.

4 Convenciones del contrato
Elemento
Regla propuesta
Base
/api/v1; servidor relativo para no inventar dominio. HTTPS y TLS 1.2 o superior.
Nombres
Recursos en plural y snake_​case en JSON. Métodos GET de lectura; POST para creación o comando; PATCH parcial; PUT para reemplazar subrecurso.
Identificadores
BIGINT se serializa como cadena decimal; UUID de comando como texto canónico. No convertir a Number en JavaScript.
Importes
DECIMAL como cadena, moneda explícita de tres letras. No usar flotantes ni asumir MXN para planes.
Instantes
RFC 3339 UTC con Z; presentación local a America/Mexico_City. Periodos [inicio, fin).
Campos
Entradas rechazan campos desconocidos. Ausente en PATCH significa conservar; null sólo limpia un campo nullable. PATCH vacío devuelve 422.
Paginación
limit por defecto 20, máximo 100; cursor opaco, next_​cursor=null al finalizar. Orden estable por fecha e ID, o secuencia para mensajes.
Errores
application/problem+json con code y trace_​id; nunca exponer SQL, stack traces, secretos ni datos de otro actor.
Concurrencia
ETag fuerte e If-Match en cambios versionados. Comparar y escribir atómicamente; 428 si falta, 412 si cambió.
Cache
Privados, sesiones y URL temporales: Cache-Control no-store. Lecturas públicas deben revalidarse para no ofrecer propiedades retiradas.
Límites técnicos
Propuesta: chat 4000 caracteres, chatbot 1000, descripciones 10000 y páginas de hasta 100. Ajustar bajo pruebas y versionar cambios incompatibles.
El cursor contiene o referencia los valores del último ordenamiento y el conjunto de filtros, protegido contra manipulación. Si se reutiliza con filtros distintos, devolver 400 CURSOR_INVALIDO. La paginación no promete una fotografía inmutable del catálogo: cada página vuelve a comprobar elegibilidad. Para mensajes no combinar cursor y after_sequence; devolver 422 si ambos se envían. El servidor limita la consulta en la base, sin descargar todas las filas para paginar en memoria.
5 Autenticación y autorización
Política
Condición efectiva
PUBLICO
No requiere token; sólo datos y operaciones públicas expresamente definidas.
ACTIVO
JWT válido, sid vigente y no revocado, cuenta ACTIVA.
GENERAL
ACTIVO y rol GENERAL; propiedad de necesidad o interés cuando corresponda.
ASESOR
ACTIVO y rol ASESOR; permite revisar expediente y regularizar plan sin conceder funciones profesionales.
PROFESIONAL
ASESOR aprobado y periodo pagado vigente; además pertenencia del inmueble y capacidad del plan.
CHAT
GENERAL con origen propio válido, o ASESOR profesional; destinatario asesor habilitado. Siempre membresía de conversación.
ADMIN
ACTIVO y único rol SUPERADMINISTRADOR; motivo y delegación al dueño del agregado.
PROVEEDOR
Firma del proveedor sobre cuerpo original, identidad del emisor, tolerancia temporal y prevención de replay según contrato aprobado.
El servidor valida algoritmo permitido, firma, issuer, audience y expiración del JWT y consulta la sesión sid. Los claims no sustituyen la lectura del estado actual de cuenta, validación y periodo. Se propone conservar el access token en memoria del cliente; al expirar se autentica de nuevo. No se introduce un refresh token sin un contrato adicional. CORS se limita a orígenes configurados y el token no viaja en URL. Las respuestas de login son genéricas para no revelar existencia de correos.
El control por recurso se aplica antes de cargar o serializar datos privados. Un identificador ajeno puede responder 404 para evitar enumeración; un permiso funcional insuficiente responde 403. Aplicar el mismo criterio en REST y WSS. Tras cinco intentos fallidos de autenticación en 15 minutos se aplica restricción temporal conforme a la línea base; el alcance por cuenta e IP, duración y límites de otras rutas se documentarán en configuración operativa y se ensayarán contra abuso.

7 Modelos de entrada y salida
El archivo openapi.json contiene todos los esquemas y sus campos requeridos. Esta sección resume su responsabilidad y mapeo; las proyecciones públicas nunca equivalen a serializar una fila completa. Las longitudes nuevas de texto y contraseña son propuestas técnicas, y deben revisarse con requisitos y pruebas antes de convertirse en restricciones de producción.

9 Flujos críticos e integridad
9 1 Publicación y capacidad
El caso de uso comprueba sesión, propiedad, validación y periodo pagado vigente. Bloquea el ámbito de capacidad del asesor y la versión de la propiedad, calcula ocupación según PD-001 y confirma estado y auditoría juntos. Dos solicitudes concurrentes por el último cupo no pueden ganar ambas. La propuesta no interpreta qué estados consumen cupo hasta resolver PD-001. La tolerancia de más de 15 días tras vencimiento no concede derechos profesionales; sólo gobierna la pausa automática.

9 2 Pago y webhook
La intención se identifica por solicitud_id persistente. Antes de llamar al proveedor se registra la intención local; el adaptador usa una clave estable si el proveedor soporta idempotencia. Ante timeout incierto, se consulta/reconcilia la misma referencia y no se crea otro cobro. Si el proveedor no permite esta garantía, la integración permanece bloqueada hasta definir recuperación. No mantener una transacción de base abierta durante llamadas externas.
El webhook recibe los bytes originales y verifica firma, emisor y vigencia antes de interpretar el evento. Comprueba la relación entre pago, versión de plan, monto, moneda y referencia económica; no confía en el navegador. Evento, pago confirmado, periodo y auditoría se confirman en una sola UoW. La unicidad de proveedor/evento evita replay del evento; la de proveedor/referencia económica evita aplicar dos eventos al mismo cobro; la de periodo/pago impide duplicar vigencia.
Eventos repetidos válidos responden 200 después de verificar que el efecto ya fue confirmado. Un fallo antes de commit se revierte y recibe un error recuperable. Reordenamientos se resuelven con transiciones permitidas y consulta al proveedor cuando sea necesaria. Reembolsos, contracargos y prorrateos requieren política adicional; no se inventa su efecto. Si falta moneda, duración o inicio del periodo no se habilitan cobros. La reactivación automática sigue condicionada a cupo y prioridad.
Figura 4. Confirmación y deduplicación del webhook. Fuente: elaboración propia a partir de los documentos 01 a 06.
9 3 Archivos privados
Se propone carga multipart a través del backend para no introducir una tabla de tickets de subida. Primero se valida identidad, propiedad, tamaño máximo aprobado, tipo real y nombre saneado. El adaptador deposita el archivo en almacenamiento privado; sólo tras verificar el objeto se confirma su referencia y metadatos en la UoW. Una segunda validación de cupo bajo bloqueo impide superar 50 fotografías.
Si falla la confirmación local, se intenta borrar el objeto recién creado y se registra su identificador en un registro técnico de compensación protegido para reconciliación. Un objeto huérfano nunca aparece en el catálogo. La transferencia no mantiene bloqueos de MySQL. El proveedor, los MIME y los tamaños siguen pendientes; no se interpreta extensión como prueba de contenido. La barra de progreso del cliente aparece cuando la carga supera dos segundos.
Las URLs de lectura requieren comprobar autorización y asociación del archivo cada vez que se emiten. Las fotos públicas siguen perteneciendo a objetos privados; una ficha retirada deja de obtener URLs nuevas. Una URL ya emitida puede seguir funcionando hasta su vencimiento máximo de 15 minutos; si se exige revocación inmediata deberá revisarse el mecanismo. Los documentos profesionales sólo son visibles al propietario por flujos que se autoricen y a revisores; esta versión sólo expone su lectura al revisor.

10 Contrato WebSocket del chat humano
Se propone WSS /api/v1/ws/chat. El navegador no puede fijar libremente Authorization en el constructor WebSocket; por ello el primer frame es una autenticación con access token. La conexión abierta no concede acceso: hasta validar el frame no hay suscripciones ni entrega de datos. Se propone cerrar a los cinco segundos si falta autenticación, limitar conexiones pendientes y validar Origin contra la lista permitida. No colocar el token en query string, logs o subprotocolos.
Tras autenticar, el backend obtiene las conversaciones autorizadas. Cada envío vuelve a comprobar cuenta, membresía y condiciones profesionales; el cierre de sesión o expiración invalida la conexión. REST y WSS llaman al mismo caso de uso. Se admite un backend de chat con una instancia en V1; escalar a varias exige resolver coordinación antes de anunciar entrega entre instancias.

11 Búsqueda chatbot y privacidad
POST /busquedas combina criterios estructurados y siempre consulta el catálogo elegible. Los identificadores de zona, tipo y operación corresponden a catálogos del MOD-03. Rangos de precios se comparan sólo en una misma moneda; no se introduce conversión cambiaria. El matching directo usa necesidad propia activa y el inverso propiedad propia elegible; sus resultados son calculados y paginados, sin tabla de historial ni notificaciones.
El chatbot utiliza TF-IDF, LinearSVC y reglas dentro del backend; no es un proveedor generativo externo. Extrae criterios reconocidos y solicita aclaración cuando falta información necesaria. El contrato no afirma que el margen de un clasificador sea una probabilidad. Los resultados se validan por el mismo puerto de catálogo; no genera propiedades inexistentes ni ofrece fichas no elegibles. Los textos libres no se incorporan automáticamente al corpus ni a logs.

13 Contrato OpenAPI y control de cambios
openapi.json acompaña a este documento como especificación completa de las operaciones HTTP enumeradas. Contiene paths, operationId, tags por módulo, seguridad Bearer, solicitudes, respuestas, parámetros y schemas. x-access-policy, x-use-case y x-gate preservan reglas de autorización y dependencias que no ejecuta OpenAPI. Estas extensiones son documentación, no mecanismos de seguridad.
La operación webhook mantiene RAW y proveedor sin firma comercial concreta: no se declara lista para integrar hasta elegir proveedor, content-type, encabezados, algoritmo, secreto y ventana temporal. El protocolo WSS de la sección 10 es complementario y no se publica como si OpenAPI validara sus frames. El contrato JSON permite revisión y validación sin copiar miles de líneas en el documento Word.
El backend implementará routers y modelos Pydantic de borde compatibles con este contrato. La salida generada de FastAPI deberá compararse con el archivo versionado en integración continua; cualquier diferencia se revisa explícitamente. El frontend consume modelos generados o comprobados contra el mismo archivo. La comprobación no exige que dominio y ORM tengan los mismos nombres o campos que el DTO.
Una eliminación de campo, cambio de tipo, nueva obligatoriedad o restricción incompatible exige plan de migración y versión mayor. Añadir campos de respuesta requiere clientes tolerantes a extensiones; entradas permanecen estrictas. Conservar una bitácora del contrato con motivo, rutas afectadas, migración, pruebas y aprobación. No renumerar los identificadores API existentes cuando se incorporen nuevas operaciones.
